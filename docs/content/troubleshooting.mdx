## "No such export" when calling exports.tDB

**Cause.** tDB has not loaded yet. Its exports all exist from its first frame,
and a call arriving before the database is up parks until it answers — so this
error means the calling resource started *before* tDB did, not that the
database is still coming up.

`@tDB/lib/MySQL.lua` waits for the database on every `MySQL.*` call, but it
cannot help if tDB itself has not started.

**Fix.**

1. Check `ensure tDB` sits above the calling resource in `server.cfg`. This is
   almost always it.
2. Confirm tDB actually started — a config error stops the resource, and the
   startup box says so.
3. If the resource must start first, wrap the call in
   `exports.tDB:onReady(function() ... end)`.

Fixed when the call runs and returns a value instead of erroring.

## "Only superusers can perform this action", repeating

**Cause.** The superuser credentials tDB is using no longer match the database.
Token expiry is *not* the cause: tDB refreshes the superuser token ahead of time,
on a schedule read from the token itself.

**Fix.**

1. Unset `tdb_superuser_email` and `tdb_superuser_password` in `server.cfg`, and
   delete the `Config.Superuser` block from `config.local.lua`.
2. Restart the resource. tDB reprovisions the superuser and writes the new
   credentials back to `config.local.lua`, printing the new password once in the
   startup box.

Fixed when the startup box reports the client authenticated.

## The PocketBase setup screen opened in my browser

**Cause.** The instance you reached is not the one tDB started. tDB always
provisions its superuser headlessly, so a setup screen means something else is
listening.

**Fix.** Look for a second PocketBase already bound to the port, and stop it.

## "Batch requests are not allowed"

**Cause.** PocketBase's batch API is off by default.

**Fix.** Enable it in **Admin → Settings → Batch API**. `runTransaction` needs
no such setting and is usually the better choice anyway.

## An error naming a SQL construct

**Cause.** That statement has no faithful SQLite translation, so tDB refused it
rather than silently changing its meaning.

**Fix.**

1. Check the name against
   [refused constructs](/docs/tDB/mysql-compatibility#refused-by-name).
2. Rewrite the statement, or move it to
   [raw SQL](/docs/tDB/pocketbase#raw-sql) and write SQLite directly.

## The admin UI is not reachable from outside

**Cause.** Most often tLib's port is closed on the host or not forwarded in NAT.
tLib cannot detect either one: it binds the port and reports its listener up
regardless of whether anything outside can reach it. After that, the causes are
`Config.ExposeAdmin`, tLib not running, or the wrong port forwarded. tDB's own
PocketBase port is internal and is never the one to forward.

**Fix.**

1. Open tLib's port — `tlib_http_port`, default 7777 — in the host firewall and
   forward it in NAT. tLib's install guide has the step, at
   [open port 7777](https://timmygstudios.com/docs/tLib/installation#open-port-7777).
   Test it from outside the network; a probe from the server itself can pass on
   a port the internet cannot reach.
2. Confirm `Config.ExposeAdmin = true`.
3. Confirm tLib is running and reports its HTTP listener up.
4. Confirm the port you forwarded is tLib's, not PocketBase's 8090.

Script access is local and unaffected either way.

## The startup box says "Waiting for tLib's HTTP listener"

**Cause.** Not an error. tLib's router isn't up yet, so there's nothing to mount
on. tDB claims the mount and logs the admin URL as soon as tLib reports ready.

**Fix.** None, unless it never clears. If it doesn't, tLib is failing to bind:
check tLib's own log and whether its port is already taken.

## The startup box tells me to update tLib

**Cause.** tLib did not report HTTP readiness, so tDB cannot know whether a mount
would work and publishes no admin URL at all. Either tLib has not finished starting,
or its HTTP listener failed — check tLib's own console output for the listener error.

**Fix.** Make sure tLib 1.0 or newer is installed and starts before tDB, then look
at tLib's startup output. Your `Config.ExposeAdmin` setting is left exactly as you
set it, and the database is unaffected, only the admin UI is.

## A script says a table does not exist

**Cause.** Its schema was never imported. tDB starts empty, and a script that
ships a `.sql` dump expects you to load it.

**Fix.** Put the dump in `tDB/sql/` and restart. See
[Importing `.sql` files](/docs/tDB/sql-imports). Then check `tdb sql status`:
a `FAILED` row names the statement that stopped it, and a `PARTIAL` row means
the schema is there but some triggers were skipped.

## Remote mode never reports ready

**Cause.** The health probe against the remote instance failed. tDB dials
`<RemoteHost>:<RemotePort>/api/health` and expects a 200 before it registers
anything.

**Fix.**

1. Confirm both `RemoteHost` and `RemotePort` are set. One alone does nothing.
2. Open that health URL from the game server itself, not from your desktop.
3. Check the remote PocketBase is reachable on that port rather than only behind
   a proxy on another one.

## Getting help

Open an issue on the
[repository](https://github.com/tommy141x/fivem-pocket-base/issues) with:

- The exact error text from the server console, as text rather than a screenshot
- The full startup box
- Your `config.lua` — it holds no credentials, so it is safe to paste as-is
- The statement involved, if it's a SQL error
